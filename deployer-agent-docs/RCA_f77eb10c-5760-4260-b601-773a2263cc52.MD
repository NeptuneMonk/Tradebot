# RCA — micro-stake-trader: production slow vs preview (trade execution + UI/WS)

**Deployment:** micro-stake-trader • **Active run:** f77eb10c-5760-4260-b601-773a2263cc52 • **Tier:** tier_0 (Starter) • **Cluster:** target-3 • **Frontend:** Cloudflare (production build) • **Prod DB:** `micro-stake-trader-pump_bot_db` (Emergent-managed Atlas, remote)

Preview runs one process against local Mongo; production runs a 2-replica pod on a 250m-CPU / 512Mi-RAM tier against remote Atlas. That gap explains every symptom. Causes ranked by impact:

---

## 1. (TOP) Pod resource starvation → OOMKills, health-check 503s, constant restarts
**Evidence:**
- `get_pod_events`: container `last_termination = OOMKilled (exit 137)`, **restart_count = 54**.
- Liveness probe failed HTTP 503 ×694; Readiness probe failed 503 ×716 (2026-09-26 → 2026-09-30).
- nginx repeatedly logs `upstream timed out ... while reading response header from upstream ... GET /health ... http://127.0.0.1:8001/health` — the FastAPI event loop is too starved/blocked to answer its own health probe in time.
- Tier ceilings (`get_tier`): CPU limit **250m**, memory limit **512Mi**. hpa/vpa disabled.
- Backend logs show `leader services started` twice within ~80 min (01:44 and 03:02) — leadership re-elected on each restart.

**Impact:** Every OOMKill/probe-kill restarts the pod, which drops the leader lease and halts all trading loops until a new leader is elected and re-warms. This is the single largest source of "unresponsive" trade execution and UI stalls. Memory pressure is aggravated by cause #5 (2.4M-doc ws_events tailing). CPU throttling at 250m starves the asyncio loop (also why /health times out and WSS keepalive pings drop — see #3).
**Fix owner:** User (raise tier in Deployment Panel → Resources) + Code (reduce memory/CPU footprint).

## 2. Multi-pod leader/relay path is ACTIVE in prod (2 replicas) — absent in preview
**Evidence:**
- `get_tier`: `replicas = 2`, `max_replicas = 2` (tier_0 forces 2). Preview = single process.
- Relay infrastructure provisioned and live in prod DB: `leader_lease` doc held by pod `...-ws674`; `pods` collection shows role `leader`; `ws_events` collection present and being written (leader field stamped on every event).
- Per code context: requests hitting a FOLLOWER are parked in `pod_commands` and polled back (RELAY_POLL_S 0.15s, EXEC_POLL_S 0.25s, RELAY_TIMEOUT_S 12s); follower WS is mirrored by tailing `ws_events` every 0.3s (WS_TAIL_S).

**Impact:** Any `/api/*` call or `/api/ws` connection that lands on the follower incurs a Mongo round-trip relay (~0.15–0.5s added latency, up to 12s worst case) instead of executing in-process as it does in preview. This adds baseline latency to trade actions and lags UI state. `pod_commands` was empty at inspection (count 0), so no relay was queued at that instant — but the path is engaged whenever both replicas serve traffic. Note: at inspection only one pod (ws674) was registered/returned; the 2nd replica is either crash-looping or not stably registering, which itself causes request failures when the LB routes to it.
**Fix owner:** Platform/tier (replica count is tier-driven) + Code (relay is inherent to >1 replica; single-replica would remove it but is a config/tier decision).

## 3. Solana WSS running on a PUBLIC endpoint → HTTP 429 rate-limit storm
**Evidence:**
- `ws_events` status doc: **`"listener_via": "public WSS"`** — the live listener is NOT on Helius.
- Backend logs: near-continuous `sol_wss ... server rejected WebSocket connection: HTTP 429; reconnecting` (dozens/min) plus `ConnectionClosedError: sent 1011 keepalive ping timeout` and one `HTTP 413`.
- Secrets: `HELIUS_RPC_URL`, `HELIUS_WSS_URL`, `SOLANA_RPC_URL`, `SOLANA_WSS_URL`, `SOLANA_RPC_FALLBACK_URL`, `SOLANA_RPC_MAX_RPS` all EXIST and are non-empty (values not inspected). Despite that, runtime fell back to public WSS.

**Impact:** A public RPC/WSS is aggressively rate-limited (429) and drops connections, so the market-data feed is in a constant reconnect loop → stale token/price data → slow, missed, or mispriced trade execution. This is a top-tier cause of "slow trade execution" specifically. The keepalive-ping timeouts (1011) also correlate with the CPU starvation in #1 (event loop can't service the socket in time). Note: value verification could not be done from here — `list_secrets` confirms presence only, not correctness, and only for the live run.
**Fix owner:** User — verify in Deployment Panel → Secrets that `HELIUS_WSS_URL` / `HELIUS_RPC_URL` / `SOLANA_WSS_URL` hold the SAME working Helius endpoints preview uses (pre-existing prod secret values are NOT overwritten on redeploy, so a stale/placeholder value persists), and that `SOLANA_RPC_MAX_RPS` matches preview. Then redeploy.

## 4. Remote managed Mongo (Atlas) vs local preview Mongo
**Evidence:** Prod DB `micro-stake-trader-pump_bot_db` is Emergent-managed Atlas (remote); preview uses local Mongo on the source pod. The hot loop does many reads/writes per tick, and the relay/mirror paths (#2) add MORE Mongo round-trips.
**Impact:** Every per-tick query now crosses the network instead of hitting localhost. Latency multiplies across the many round-trips per tick, and this same latency sits in the critical path of the follower relay (#2) and ws_events tail (#5).
**Fix owner:** Code (reduce per-tick round-trips / batch) + Platform (region co-location, if Atlas and pod differ in region).

## 5. `ws_events` capped/mirror collection bloated to ~2.4M documents
**Evidence:** `ws_events` count = **2,412,332** docs. Followers tail this every 0.3s; leader writes every event (scanner_skip, wallet, status, …).
**Impact:** A 2.4M-doc collection makes the tail scan and writes heavier, adds to remote-Mongo load (#4) and to pod memory pressure (#1). Contributes to both OOM and mirror lag.
**Fix owner:** Code — confirm the collection is actually capped (size-bounded) and/or trim retention; reduce event write volume.

- **WebSocket upgrade:** The APP↔Solana upstream WSS is failing (429/1011 reconnect storm). The client↔`/api/ws` path routes to backend via nginx `/api` (WS upgrade map present in template); no client-side 101/upgrade rejection seen, but backend restarts (#1) force client reconnects. - **Build/pipeline differences:** Frontend IS a production build (hashed bundle `main.a0bef777.js`, served from Cloudflare/R2) — not dev mode. Backend runs a single uvicorn worker (entrypoint strips `--reload`); starved by the 250m CPU ceiling rather than by worker count.

## Recommended order of remediation
1. Verify/fix `HELIUS_WSS_URL`/`HELIUS_RPC_URL`/`SOLANA_WSS_URL`/`SOLANA_RPC_MAX_RPS` values in Secrets → stop the public-WSS 429 storm (biggest trade-latency win, cheapest fix). Redeploy.
2. Raise tier (Resources) to end OOMKills + health-probe restarts + CPU starvation.
3. Code: cap/trim `ws_events`, reduce per-tick Mongo round-trips; consider whether the app can run single-replica to avoid the relay path.
